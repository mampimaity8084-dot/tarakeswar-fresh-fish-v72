# V4.3 Payment Flow

Status: isolated development candidate only. This document does not authorize a production change.

## V4.2 current flow

The customer browser submits cart/customer data to `create-checkout.js`. The function validates current products and pricing, creates a Razorpay order, and writes a `payment_sessions` record. The browser completes Razorpay Checkout and calls `verify-checkout.js`. That function verifies the signature and Razorpay payment, then calls `finalize_payment_session_v3` to create/finalize the Supabase order. `create-order.js` and `verify-payment.js` remain parallel compatibility endpoints.

## V4.3 proposed flow

1. Browser sends customer/cart/delivery data to `create-checkout.js`.
2. Server normalizes input and re-reads product prices, availability, minimum order, discount, capacity, and payable amount from Supabase.
3. Server creates a single payment session with a request/idempotency key and a server-calculated amount.
4. Server creates the Razorpay order and stores the Razorpay order ID.
5. Browser opens Razorpay Checkout using only the public key and server response.
6. Browser sends Razorpay order ID, payment ID, signature, and payment-session ID to `verify-checkout.js`.
7. Server verifies the signature, confirms Razorpay order/payment/amount/currency, captures authorized payments where required, and locks finalization.
8. Server calls the database finalization RPC exactly once. Repeated callbacks return the existing finalized order rather than creating another order.
9. Customer receives order number and a controlled delivery-OTP response. OTP is not included in generic public order-list responses.

## Failure and retry handling

- Invalid input: 4xx, no payment session.
- Product/price/slot change: reject before payment creation.
- Razorpay creation failure: session remains failed/abandoned; no order.
- Signature/payment mismatch: reject and record verification failure.
- Duplicate callback: return the previously finalized order.
- Finalization timeout: retry using the same session lock; never insert a second order.
- Unknown provider state: leave session pending and require reconciliation.

## Rollback

No production rollback is needed because this candidate is isolated. In a future approved rollout, revert the browser to the V4.2 compatibility endpoints, keep the compatibility functions available, and do not remove the V4.3 payment-session columns until all pending sessions are reconciled.
